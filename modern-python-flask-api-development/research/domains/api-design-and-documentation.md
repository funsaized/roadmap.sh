# API Design and Documentation

## Overview

This domain covers the principles and tools for designing well-structured REST APIs with Flask, generating OpenAPI/Swagger documentation automatically, implementing pagination/filtering/sorting, and managing API versioning. It builds on D-4 (Request Handling and Data Validation) and feeds into D-10 (Security Hardening) and D-13 (Advanced Architectural Patterns).

## Key Concepts

### 1. OpenAPI Specification (OAS)
The OpenAPI Specification (formerly Swagger Specification) is a standardized, language-agnostic format for describing REST APIs. Version 3.1 introduced full JSON Schema compatibility. An OpenAPI document includes metadata (`info`), server connectivity (`servers`), endpoints (`paths`), reusable definitions (`components`), and security schemes. It can be written in YAML or JSON and serves as both documentation and a contract for API consumers.

**Relationship:** Foundation for all auto-documentation tools; consumed by Swagger UI, ReDoc, and code generators.

### 2. Swagger UI and ReDoc
Interactive documentation renderers that consume OpenAPI specs. Swagger UI provides a "try it out" interface for testing endpoints directly in the browser. ReDoc offers a clean, three-panel documentation layout. Both are bundled or easily integrated with Flask extensions.

**Relationship:** Presentation layer for OpenAPI specs generated by Flask-RESTX or flask-smorest.

### 3. Flask-RESTX
A community-maintained fork of Flask-RESTPlus that provides decorators and tools for building REST APIs with automatic Swagger UI generation. Key features:
- **Namespaces** for organizing endpoints into logical groups
- **`api.model()`** for defining request/response schemas that map to OpenAPI components
- **Response marshalling** with `@marshal_with` for consistent output formatting
- **Request parsing** with `reqparse` (legacy) or model expectations with `@expect`
- **Decorators**: `@ns.doc()`, `@ns.response()`, `@ns.param()` for enriching documentation

**Relationship:** Alternative to flask-smorest; uses its own model system rather than Marshmallow.

### 4. flask-smorest
A Flask extension built on top of Marshmallow and webargs that generates OpenAPI 3.x specs automatically. Key features:
- Uses **Marshmallow schemas** for both validation and documentation (single source of truth)
- **Blueprint-based** architecture for organizing API resources
- **`@blp.arguments()`** and **`@blp.response()`** decorators for request/response documentation
- Built-in pagination support
- Generates OpenAPI JSON at `/openapi.json`

**Relationship:** Integrates tightly with Marshmallow (covered in D-4); preferred for projects already using Marshmallow for validation.

### 5. APIFlask
A lightweight Flask wrapper built on flask-smorest that provides an even more streamlined experience for building OpenAPI-documented APIs. Features include automatic spec generation, built-in validators, and a simplified decorator API. ~1.1k GitHub stars.

**Relationship:** Higher-level abstraction over flask-smorest; good for new projects wanting minimal boilerplate.

### 6. API Versioning Strategies

#### a) URI Path Versioning
Version embedded in the URL path: `/api/v1/users`. Most common and explicit approach. Easy to implement with Flask Blueprints — register versioned blueprints with different URL prefixes.

#### b) Header-Based Versioning
Version specified via HTTP headers: `Accept: application/vnd.myapp.v1+json` or custom `X-API-Version` header. Keeps URLs clean but harder to test in browsers.

#### c) Query Parameter Versioning
Version as a query parameter: `/api/users?version=1`. Simple but not RESTful convention. Generally discouraged for production.

#### d) Content Negotiation (Media Type Versioning)
Uses vendor-specific media types in the `Accept` header. Most "REST-pure" approach but complex to implement and maintain.

**Best practices:** Choose one strategy and be consistent. Use Flask Blueprints to modularize versions. Support at least current and previous major version. Plan versioning from day one.

### 7. Pagination Strategies

#### a) Offset-Based Pagination
Uses `page` and `per_page` (or `offset` and `limit`) parameters. Maps directly to SQL `LIMIT/OFFSET`. Simple but degrades with large offsets ("deep paging problem") and suffers from data drift (items skipped or duplicated when data changes between requests).

#### b) Cursor-Based Pagination
Uses an opaque cursor token (often base64-encoded) pointing to the last item. Client sends cursor to get next page. Consistent performance regardless of depth. No skipped/duplicated items. Cannot jump to arbitrary pages. Ideal for infinite scroll UIs.

#### c) Keyset Pagination (Seek Method)
Uses actual column values from the last record (e.g., `created_at > '2024-01-01'`) rather than opaque cursors. Leverages database indexes for optimal performance. Most efficient for large datasets but requires unique, sortable keys.

**Comparison summary:**
| Strategy | Performance | Consistency | Random Access | Complexity |
|----------|------------|-------------|---------------|------------|
| Offset | Degrades with depth | Poor with mutations | Yes | Low |
| Cursor | Constant | Good | No | Medium |
| Keyset | Optimal | Excellent | No | Medium-High |

**Flask implementation:** Flask-SQLAlchemy's built-in `paginate()` method provides offset-based pagination with a `Pagination` object containing `items`, `total`, `pages`, `has_next`, `has_prev`, etc.

### 8. Filtering and Sorting
Techniques for allowing API consumers to narrow and order results via query parameters:
- **Filtering:** `?category=electronics`, `?price[gte]=10&price[lte]=100`, or `?name__eq=widget`
- **Sorting:** `?sort_by=price&order=desc` or `?sort=created_at:desc,name:asc`
- **Security:** Always whitelist allowed filter/sort fields to prevent injection attacks
- **ORM integration:** Map query params to SQLAlchemy `.filter()`, `.filter_by()`, and `.order_by()` calls

**Relationship:** Combines with pagination for complete collection endpoint design. Prerequisite for D-10 (ensuring filter params are sanitized).

### 9. HATEOAS and Hypermedia
Hypertext As The Engine Of Application State — REST maturity level 3. API responses include links to related resources and available actions. Example: a paginated response includes `next`, `prev`, `first`, `last` links. While not universally adopted, it improves API discoverability.

**Relationship:** Advanced concept connecting to D-13 (Advanced Architectural Patterns).

### 10. API Design Best Practices
- Use plural nouns for resource names (`/users`, not `/user`)
- Use kebab-case for multi-word URL paths (`/product-orders`)
- Return appropriate HTTP status codes (201 for creation, 204 for deletion, etc.)
- Wrap responses in envelope objects for extensibility
- Provide meaningful error responses with consistent structure
- Use `operationId` in OpenAPI specs for code generation
- Design-first vs code-first approach to API specification
- Include examples in schemas for better documentation

### 11. Response Envelope and Error Formatting
Standardized response structure wrapping data in a consistent format:
```json
{
  "data": [...],
  "pagination": {"page": 1, "total": 100},
  "errors": null
}
```
Error responses should include error code, message, and field-level details for validation errors.

### 12. Rate Limiting Documentation
Documenting rate limits in API responses via headers (`X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`) and in OpenAPI specs. Important for API consumers to handle throttling gracefully.

**Prerequisite for:** D-10 (Security Hardening) where rate limiting is implemented.

## Learning Path

### Phase 1: OpenAPI Fundamentals (3-4 hours)
1. Read the OpenAPI 3.1 overview at https://learn.openapis.org/best-practices.html
2. Understand the structure of an OpenAPI document (info, paths, components, schemas)
3. Learn about Swagger UI and ReDoc as documentation renderers
4. **Milestone:** Can read and write a basic OpenAPI spec by hand in YAML

### Phase 2: Auto-Documentation with Flask Extensions (6-8 hours)
1. Set up Flask-RESTX with namespaces, models, and Swagger UI
2. Learn `@ns.doc()`, `@ns.expect()`, `@ns.marshal_with()`, `@ns.response()` decorators
3. Set up flask-smorest with Marshmallow schemas and Blueprint architecture
4. Compare Flask-RESTX vs flask-smorest: model system vs Marshmallow, feature parity
5. Explore APIFlask as a higher-level option
6. **Milestone:** Build a CRUD API with fully auto-generated interactive documentation

### Phase 3: Pagination, Filtering, and Sorting (5-6 hours)
1. Implement offset-based pagination with Flask-SQLAlchemy's `paginate()`
2. Understand cursor-based and keyset pagination — when and why to use each
3. Add filtering via query parameters with field whitelisting
4. Add sorting with configurable sort fields and directions
5. Return proper pagination metadata in responses
6. **Milestone:** Collection endpoint with pagination, filtering, and sorting all working

### Phase 4: API Versioning (3-4 hours)
1. Understand the four versioning strategies (URI, header, query param, content negotiation)
2. Implement URI path versioning using Flask Blueprints (`/api/v1/`, `/api/v2/`)
3. Learn to share business logic between versions while varying API contracts
4. Plan deprecation strategy and migration guides
5. **Milestone:** Two API versions running in parallel with shared service layer

### Phase 5: API Design Best Practices (3-4 hours)
1. Study RESTful naming conventions (plural nouns, kebab-case paths)
2. Design consistent error response formats
3. Implement response envelopes with metadata
4. Add HATEOAS links to paginated responses
5. Understand design-first vs code-first approaches
6. **Milestone:** Refactored API following all best practices with comprehensive docs

**Total estimated time: 20-26 hours**

## Practical Exercises

### Exercise 1: Auto-Documented CRUD API (Beginner)
Build a bookstore API with Flask-RESTX or flask-smorest that has full Swagger UI documentation. Include models for Books, Authors, and Categories. Ensure all endpoints show proper request/response schemas in the docs.

### Exercise 2: Pagination Strategy Comparison (Intermediate)
Create a single endpoint (`/products`) that supports three pagination modes:
- `?mode=offset&page=2&per_page=10`
- `?mode=cursor&cursor=abc123&limit=10`
- `?mode=keyset&after_id=50&limit=10`

Benchmark all three with 100k records. Document trade-offs observed.

### Exercise 3: Filtering and Sorting Engine (Intermediate)
Build a reusable filtering/sorting module that:
- Accepts `?filter[field]=value` and `?sort=field:direction` patterns
- Whitelists allowed fields per model
- Translates to SQLAlchemy queries
- Documents available filters in OpenAPI spec

### Exercise 4: Multi-Version API (Advanced)
Create an API with v1 and v2 using Flask Blueprints:
- v1 returns flat user objects
- v2 returns nested user objects with embedded address
- Both versions share the same service layer and database
- Swagger UI shows both versions with proper grouping

### Exercise 5: Design-First API (Advanced)
Write an OpenAPI 3.1 spec first (in YAML), then implement the Flask API to match it exactly. Use a spec validation tool to verify your implementation matches the contract. This teaches the design-first workflow.
